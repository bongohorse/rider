## Ownership and state

- **Native Defold GUI:** [`ui.gui_script`](../../main/game/ui.gui_script) creates station/diagnostic metrics, tuning controls and the [`run_ui.lua`](../../main/game/run_ui.lua) run HUD/result card; [`progress_ui.lua`](../../main/game/progress_ui.lua) owns native progress. [`layout.lua`](../../main/game/layout.lua) uses a 960×540 authored space with anchored roots, uniform panel scaling and a text-readability floor. `gui.set_safe_area_mode(gui.SAFE_AREA_BOTH)` is set at UI initialization. Desktop uses the native clock/best/coin/fuel surfaces; the result card, Retry and Levels/Next Level buttons are native on both input modes.
- **HTML5 touch DOM:** [`mobile.js`](../../main/game/mobile.js) creates `#rider-mobile` toolbar, readout, progress, fuel/coins, touch zones and toast. `touch=1` forces it; `touch=0` disables it. Its DOM readout replaces several native running labels in touch mode; native metrics remain visible. The [`level_menu.js`](../../main/game/level_menu.js) DOM overlay is separate, hides its floating actions during tuning and has its own safe-area handling.
- **Input ownership:** touch zone `pointerdown`/capture/release is translated by [`mobile.lua`](../../main/game/mobile.lua) into normalized commands for the existing owner, not a second physics loop. DOM toolbar clicks clear held touch commands; native GUI `run_ui.input` routes Retry to the run owner and Levels/Next Level to the loader. Editor mode disables native driving roots; tuning hides touch zones and readout. Terminal run states show the native result card, hide native running fuel and disable the touch toolbar Pause; canonical Retry remains available.
- **Time invariant:** [`game.project`](../../game.project) has display update frequency 60, fixed update frequency **60 Hz**, physics fixed timestep enabled and four Box2D solver substeps. This UI audit changes none of those settings, owner callbacks or world state.

## Prioritized follow-ups

These are **source-backed usability risks**, not confirmed current-head bugs. They require independent, small implementation GOs after geometry measurement.

1. **P1 — Crowded touch toolbar and undersized secondary targets.** [`mobile.js`](../../main/game/mobile.js) sets toolbar buttons to **32 px minimum height** (general buttons are 44 px), places many actions in a wrapping flex row and fixes the readout at `top:100px`. Historical 1080×486 screenshots show two rows already. The toolbar/readout bounds are not jointly asserted by the current touch tests. **Minimal reversible follow-up:** prioritize Retry/Pause/Tuning and move less-frequent actions to a discoverable secondary group, with a shared measured toolbar/readout layout; do not just increase heights without checking the extra wrap. **Acceptance:** at 1280×720 desktop, 1080×486 and 960×540 synthetic touch, and a narrow/portrait fallback, all visible actionable touch targets are at least 44×44 CSS px, remain inside the safe area and do not intersect readout, level actions or drive zones; Retry, pause/resume, Tuning, Import, Layout mirror, tilt and simultaneous drive/lean still work through real input. **Risk:** changing toolbar focus, held-pointer cancellation, tuning and accessibility; keep existing `check_mobile.cjs`, `tools/preview/mobile.cjs` and `check_levels.cjs` behavior assertions.

2. **P2 — Competing information and Retry actions in compact touch mode.** [`ui.gui_script`](../../main/game/ui.gui_script) keeps the speed/suspension/FPS native metric group in view while [`mobile.js`](../../main/game/mobile.js) also shows a DOM readout; [`run_ui.lua`](../../main/game/run_ui.lua) shows native Retry on terminal states while the DOM toolbar also exposes Retry. Both Retry controls appear in the historical finished screenshot. **Minimal reversible follow-up:** define one primary compact touch Retry affordance and separate essential driving status from optional diagnostics, preserving the existing canonical reset route and access to diagnostics via Tuning. **Acceptance:** in ready/running/paused/finished/failed states, essential time/best, fuel, coins/gems and progress remain available without duplicated primary actions; after finish exactly one visually primary Retry is offered, and it still resets the same world with held input cleared. Verify both desktop and synthetic touch. **Risk:** accidentally hiding important fuel/progress or breaking native Android's result controls; do not simply remove native Retry globally.

3. **P2 — Fixed result-card text capacity is not covered by geometry assertions.** [`run_ui.lua`](../../main/game/run_ui.lua) positions a **440×220 authored-unit** card, a fixed `coins` text node and separate medal/next/Retry labels. Coin and Wonder Gem status can be multiline; storage-error and practice strings have variable lengths. Current release tests assert **text content**, not that all these nodes fit at 960×540/1080×486 or on a native phone. **Minimal reversible follow-up:** measure rendered node/text bounds in finished/failed, practice, unsaved-best and gems-present states; only then adjust card spacing/wrapping or a bounded responsive layout, preserving visible controls and source strings. **Acceptance:** no clipped/overlapping text or action targets at the two landscape sizes, including longest existing status strings; saved-best/medal/gem semantics and real-pointer Retry/Levels/Next Level tests remain unchanged. **Risk:** changing native GUI hit targets and Android scaling; avoid touching the level editor or physics.

## Play bar (#678)

Claudio's zone layout of 2026-11-09 (debug card top left, player strip top centre, one button row top right, reserved callout and edge areas, drive zones only at the bottom on touch) is built in slices. **Slice 1, the button row:** in HTML5, desktop and touch, [`play_bar.js`](../../main/game/play_bar.js) draws one row in the editor kit style. It holds Retry (circular arrow), Pause/Resume (a normal button while driving, green Play while paused), Tuning (`Close tuning` while open), 3D look, Edit level, Levels and More. More holds Help and, on desktop, Import level, Quality and Fullscreen. On touch it holds the adapter's existing tools, which already include those three. Commands use the existing owners:
- Retry and Pause are the touch adapter's one-shot requests (`riderMobile.request`, read by the controller), on desktop too.
- Levels uses `riderLevelsRequest`, and Import uses `riderCustom`.
- Tuning, Help, 3D and Edit level are queued for `ui.gui_script` (`toggle_tuning`, `toggle_help`, `terrain_look_open`, `editor_enter`).

The row replaces the touch toolbar's own buttons, the native T/H/Pause and run Levels buttons, the floating Levels button (Next Level stays), the page buttons while driving and the Play-mode 3D/Edit hints. In HTML5 the native top-right group (tuning panel, Record/Replay) starts 60 authored units lower (`layout.right_top_inset`) and the play-mode 3D panel starts below the row, so the row never moves. The bar, the editor chrome and the Levels dialog live inside `#app-container`, the fullscreen element. A second press on 3D closes the 3D look. The FPS counter and the camera control avoid the row like any DOM control. The native HUD remains the fallback outside HTML5.

**Slice 2, the player strip:** the play bar also draws, top centre, the run time, the run state with best, medal/official/practice and save state, coins (with the pickup flash), Wonder Gems (when the course has any) and a fuel bar (amber when low). It reads `riderRun`, `riderCoins`, `riderFuel` and `riderProgress`, as the touch readout did. Under it, a progress bar shows a start flag icon, a filled track with a marker, a finish flag icon and the percentage (Claudio: icons instead of "Start"/"Finish"); an unavailable course shows its reason. The strip is centred when there is room; otherwise it ends left of the button row and moves the status line to a second row, so it clears the debug corner. In HTML5 it replaces the native clock/best, running coin line, fuel bar and progress bar (their texts and geometry are still computed for the checks) and the touch readout's run, coin, fuel and progress lines. The readout keeps its station, tilt, replay and status lines. The camera control avoids the strip like the touch readout.

**Slice 3a, the debug group:** on desktop in HTML5 the native Next station, Section, Speed, Record and Replay buttons and the free-camera button are one kit-styled group at the bottom left. Each keeps the visibility rule of the button it replaces: no Next, Speed, Record or Replay during a timed run; no Record or Replay while tuning is open; Section only on courses with more than one section. Each sends the same message: `select_station`, `next_section`, `time_control step`, `replay_control`, or the free camera's `set`. Touch keeps these tools in More. `riderHud` no longer publishes `step`, `record` or `replay` in HTML5.
