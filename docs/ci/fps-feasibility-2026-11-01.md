## Pinned source and invariant

- Rider pins **Defold/Bob 1.14.0**, source [`a81dbb0478e8b73931dc2d671563204f6ac0ef82`](https://github.com/defold/defold/tree/a81dbb0478e8b73931dc2d671563204f6ac0ef82) ([toolchain lock](../../tools/toolchain-lock.json), [engine references](../ENGINE_REFERENCES.md)). Official stable **1.14.0** [`sys` API reference](https://defold.com/ref/sys-lua/) and [project settings](https://defold.com/manuals/project-settings/) are the API sources used here. These document the API contract, **not** measured Rider behavior on any device.
- Rider's [`game.project`](../../game.project) sets `display.update_frequency=60`, legacy `display.vsync=0`, `engine.fixed_update_frequency=60`, `physics.use_fixed_timestep=1` and `box2d.sub_step_count=4`. Preserve all five settings for this feasibility stage. A solver substep is **not** a gameplay `fixed_update` tick.
- `sys.set_update_frequency(frequency)` is a documented **runtime game-update/frame-cap request** equivalent to `display.update_frequency`. A positive value requests timer pacing on platforms where Defold owns the application loop; `0` requests variable-rate updates and restores the requested swap interval. `msg.post("@system:", "set_update_frequency", {frequency=...})` is a documented alternative. Neither changes `engine.fixed_update_frequency` by definition. The API explicitly warns that a cap may not be achieved, and engine `update(dt)` is not necessarily constant; elapsed time beyond `max(engine.max_time_step, 1/frequency)` may be discarded on hitches. [Official API](https://defold.com/ref/sys-lua/#sys.set_update_frequency:frequency).
- `sys.set_vsync_swap_interval(interval)` is a **separate presentation request**, not a deterministic render-rate setter. Positive update-frequency pacing requests swap interval 0 where supported; driver/backend may override vsync. `sys.set_render_enable` disables rendering, not an FPS preference. [Official API](https://defold.com/ref/sys-lua/).

**Non-negotiable invariant:** one Defold-owned Box2D world and controller tick owner; **60-Hz fixed callbacks** with `dt=1/60` at normal time factor 1, **four Box2D solver substeps per physics step**. No manual `b2d` stepping, second clock, frame-based input injection, variable physics dt or changed physics project settings.

**Terminology:** `requested target` is an API input; `update cadence` counts Defold `update()` callbacks; `render/presentation cadence` counts actual frames shown; `refresh rate` is the display's hardware mode; `fixed cadence` counts `fixed_update()` callbacks and their `dt`. They are not interchangeable. A 30-update/60-fixed regime ideally averages **two fixed ticks per displayed update**; a 60/60 regime averages one, but startup, stalls, pause and scheduling can change individual-frame ratios. Auto has no fixed ratio.

## Existing ownership and UI

- [`main/gym/controller.script`](../../main/gym/controller.script) owns `update(self,dt)` (around line 304) and **the sole** `fixed_update(self,dt)` (around line 546). It tracks `fixed_ticks`, `time_scaled_ticks`, `world_time`, checks `dt*60` for comparable debug cases and records/replays **one command per fixed tick**. Render-frame timing comes from `mobile.poll(frame_dt,...)` in `update`; its `frame_dt` is divided by the world time factor and deliberately becomes zero on pause. **Do not** infer physics cadence from this phone FPS readout.
- [`main/gym/boot.script`](../../main/gym/boot.script) is the **world collection-proxy time-scale owner** (`time_control`, `time_ready`, around lines 349–373). It applies 1, 0.5, 0.25 or 0 via the proxy; these are pause/slow-motion controls, **not** display FPS settings. The [physics contract](../contracts/physics.md#pause-slow-motion-and-live-tuning) documents that paused worlds have no fixed steps, but their render `update` can continue.
- [`main/gym/mobile.js`](../../main/gym/mobile.js) offers `60 Hz`, `144 Hz`, `Other / adaptive` under **Measure** (around lines 191–201). This select records the **phone refresh mode selected externally** as `refreshModeUserSelected` and aborts a measurement on change; it **never** calls an engine FPS setter. Preserve that meaning. The existing 30-second recorder measures callback intervals, not hardware refresh, presented frames or fixed tick counts.

## Future minimal implementation

**Separate future issue and maintainer GO required.** Do not modify `game.project` or runtime now.

1. First add a **debug-only read-only** cadence probe in a separate issue: count Defold `update` and `fixed_update` callbacks with monotonic wall-clock windows; report `dt` distributions, time factor, focus/visibility, build SHA and real vs simulated time. For HTML5 additionally record browser `requestAnimationFrame` intervals as a **browser presentation proxy**, explicitly not proof that a Defold frame was presented. Native Android needs on-device frame-presentation tooling or direct observation for actual display cadence. Avoid reading `mobile.poll`'s pause-zeroed dt as an unscaled source.
2. If a platform demonstrates a safe, repeatable runtime cap, put an **independent Display FPS** preference in the player settings menu (not the editor, tuning speed or Measure refresh selector): `Auto` / `60` / `30`, **only for proven modes**. Show **requested** and **measured update FPS** separately, plus a clear unsupported/limited indication; never silently claim an unachieved target. Default stays existing 60 request until a separate decision.
3. Candidate persistence: a distinct, versioned `rider` settings record using the documented [`sys.get_save_file`, `sys.load`, `sys.save`](https://defold.com/ref/sys-lua/) APIs. Do not reuse or overwrite coin/best/progression slots. Reuse Rider's existing HTML5 persistence/sync acknowledgement semantics rather than treating an unsynced write as durable. On unsupported platforms or failed load, fall back to the current default; changes must not alter race records, world time factor or replay data.
4. Only one designated application-level owner may request `sys.set_update_frequency` after loading a validated setting. Never let each loaded proxy or a per-frame HUD callback set it; reapply on app startup only as verified. No separate simulation scheduler or manual interpolation by default.

## Decision and evidence limits

**Feasibility verdict, 2026-11-01:** a real runtime **API request** exists in Defold 1.14.0. **A cross-platform guaranteed 30/60 FPS player setting is not established**, especially for browser-controlled HTML5. The safest next step is a tiny cadence-probe implementation issue after explicit GO, then an independently approved platform-gated setting only if measurements support it. This audit itself delivers **no FPS improvement or new option**.

**Verification performed:** read current Rider `game.project`, `controller.script`, `boot.script`, `mobile.js`, physics contract, platform matrix, toolchain lock and the Defold 1.14.0 stable System API/project-settings pages. **NOT RUN:** local Defold build, Node tests, Playwright, HTML5 runtime setter, Android APK/device, physical FPS/presentation measurement, CI. No current-head CI result is claimed.
