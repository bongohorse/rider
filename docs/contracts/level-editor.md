# Level editor contract

Binding rules for the developer level editor ([epic #118](https://github.com/bongohorse/rider/issues/118), milestone **Level Editor**, tasks LE1a–LE6: #122–#129, plus LE5c [#186](https://github.com/bongohorse/rider/issues/186)). The epic holds goal, decisions D-E1…D-E13, user flow, task order, out-of-scope items, later candidates and research. **This file is the single source for the rules below**; change them only by PR. Gameplay objects (#120) and visual authoring (#121) are outside this contract.

Rules apply from the task named in them; a task issue lists the rules it implements. Where engine behaviour is assumed, verify it against the pinned engine ([engine references](../ENGINE_REFERENCES.md)) and record the sources in the PR.

## Rules (R1–R18)
**R1 Source vs. compiled data.** In the editor the **source objects** (lines, curves, prefabs, connections) are authoritative. Play and Export always **recompile** `chains`/`hulls`/`labels`/`spawn`/`start_speed`/`finish`/`bounds` from them (full field contract in "Data model"). The `editor` block carries its own `editor_version` and `compiler_version` **from the first saved draft (LE2)**. Opening never silently overwrites geometry:
- **Known/supported editor and compiler versions, unexpectedly different compiled data for the same source revision:** show the difference; the user deliberately chooses "keep compiled geometry (open as lines)" or "recompile from source".
- Track source revision and the revision/version used to compile the cached geometry. An autosaved edit may intentionally have stale or absent compiled data; reopening it must not report an unexpected mismatch merely because Play has not been pressed.
- **Unknown/newer editor or compiler version:** never automatically recompile using unsupported semantics. Either open supported existing compiled data as an editable line copy or refuse to open. The original file and unknown source data are preserved unchanged. LE2 safely rejected unsupported versions; LE4 adds the compatibility handling ([document management](#document-management-le4)).

**R2 Old stations are not decomposed.** Stations without an editor block open as **editable polylines and hulls**. No automatic recovery of parametric prefabs is promised. (Later option: replace a selected point run by a prefab.)

**R3 Templates drop station-specific measurement data.** "Open as template" creates a generic custom level (**`kind` omitted**, new custom id/name) and **removes `sections`, `markers` and other kind-specific measurement data** by a fixed, tested rule. The built-in original stays untouched and read-only. **LE2** provides minimal access (open a built-in station as a template copy); full template browsing is LE4.

**R4 Explicit connection model.** Pieces are connected by an explicit **connection record** (end A ↔ end B), never inferred from coincident coordinates. v1 supports **simple linear terrain runs** (each end has at most one connection); branches are deferred. Edit rule for v1:
- On a parameter/shape change of a piece, its **entry stays fixed**; the **whole downstream run is translated** by the displacement of the piece's exit. **No automatic rotation or deformation** of other pieces.
- Upstream pieces never move on a parameter change.
- **Dragging** any piece translates the **whole connected run**. To move only part of a run, disconnect first.
- An edit that cannot keep all connections (e.g. a closed loop, a downstream piece pinned by another connection) shows a **visible conflict** and is not applied silently.
- The user can deliberately **disconnect**. The edit including all moved pieces is **one undo step**. A connected run compiles into **one chain** (A18/D8: abutting pieces cause ghost bumps); only the open jump gap of a Kicker + landing prefab splits it ([prefabs](#prefabs-le5a)).

**R5 Snapping ≠ connecting.** Snapping only positions and shows the target. A connection exists only when confirmed or via explicit **Connect / Disconnect** actions. **Deliberately placing a prefab at a free end** (with a visible connect preview) counts as confirmation and connects automatically; mere proximity or hover never connects. Two coincident points may stay unconnected (e.g. stacked paths).

**R6 Snapping rules.**
| Input | Effect |
|---|---|
| Default | 0.5 m grid + anchor snap |
| Alt held | 0.1 m grid |
| Shift held | 15° angle steps |
| Ctrl held while dragging | all snapping temporarily off |
| G | toggle grid snap persistently |

Precedence: anchor snap > angle snap > grid snap. With Shift, the point lies on the 15° ray and the grid applies to the length along that ray. Alt/Ctrl behaviour is verified in the target desktop browsers (e.g. Alt opening the browser menu, Alt+drag moving the window on some Linux window managers); if a key is unusable, a replacement key is defined in the PR. Wheel and middle button must not scroll the page. The active snap is always visible (indicator + status bar). Grid drawn at a readable density for the current zoom.

**R7 Size limits are measured per layer.** Today every chain segment creates its own line sprite (`stations.lua`), the validator caps render objects at 800, a chain at 2048 points and a level at 32 chains; the **current project setting** (`game.project`) is `max_count` 1024 for sprites and labels. GUI nodes have their own per-scene limit. Sprite, label and GUI budgets are recorded separately. LE1b measures rendering, physics and geometry cost separately **only within the unchanged validation limits** and reserves headroom for editor overlays (handles, grid, selection); a render-budget failure is not evidence of a physics limit. Cases above the limits are documented as rejected; their physics cost is reported as **unknown** (no extra measurement harness beyond the limits). The real editor cost is **re-checked in LE3** (lines, handles, snapping) and **again in LE5a/LE5b** (prefabs, curves). The sprite budget is a known limiting factor, but whether build time, memory or physics also matter is an LE1b **measurement result**, not an assumption. **Release-capable rendering:** debug `draw_line` does not render in release builds, and the editor ships in the release build (D-E4), so grid, lines and handles use sprites, GUI nodes or a mesh and count against these budgets. Hiding sprites does not free component budget (to be verified against the pinned Defold version). Changing the terrain rendering is allowed if measurement shows it is the bottleneck (see "Terrain rendering optimisation" in the later candidates of #118).

**R8 Adaptive curve sampling.** Redundant collinear source points are simplified first; curves are then sampled adaptively with a maximum shape deviation and a deliberately chosen maximum segment length. Simplification must not invalidate the final sampling constraints or remove intentional corners. The actual reduction on real courses is measured, not assumed. Sampling depends only on the source data and compiler settings, **never on zoom**. Settings and method: [curves and sampling](#curves-bumpwave-and-sampling-le5b).

**R9 Unplayable drafts can be saved.** Drafts may be open, incomplete or invalid (e.g. a fresh "New" level with no terrain, which the validator rejects as empty). Structurally valid drafts can be saved/restored even when their terrain is not playable, subject to explicit storage limits and reported save failures (R12, R14). **Play** and **Export as playable station** require valid compiled data and show the validation errors otherwise.

**R10 Test start is precise and temporary.** Two explicit modes:
- **Start on surface:** vehicle preview placed **upright** on the surface below the cursor with the correct clearance; default 0 m/s. (Aligning to the slope is a later option if drive tests need it.)
- **Drop here:** exact position in the air; default 0 m/s.

A start speed is an explicit option. Invalid positions (inside geometry, no surface below for "Start on surface", **outside the level bounds**) are shown and refused. A test start never changes the persistent START marker and is **never exported**. Permanent START placement also checks clearance for the complete upright vehicle, not only its centre; overlap with terrain/hulls blocks Play with a useful error. Temporary and permanent spawn previews use the same placement rules.

**R11 Edit ↔ Play.** **E in the editor does exactly what Play does**: compile, validate, and start a **new** test run from the start marker (or show the errors and stay in the editor). **E while driving** returns to the editor at the **last editor camera view** (not the driving camera), with nothing lost. **Play** / Enter = same as E in the editor. **R works only while driving** and repeats the last test start (retry); R is disabled in the editor. There is never a continuation with old contacts or velocities.

**R12 Autosave and recovery.** Autosave after **completed actions** (a whole drag, not every mouse move), briefly debounced. Status shows **Saved / Unsaved / Save failed**. The last working state is kept. Import is validated first and opens as a **copy**; no existing level is silently overwritten.

**R13 Automatic bounds.** Safety bounds are computed automatically **from every geometry compile, from LE2 on**, from terrain, hulls, START and FINISH plus a margin. These bounds are used for test runs, saving and export alike. **Temporary test starts never change the bounds**; a test start outside them is refused (R10). There are no stale hand-set bounds in custom levels. LE6 only adds bounds display/comfort.


**R14 Safe custom loading and storage (LE1a onward).** Custom-level replacement is serialized through the existing world-switch owner (`boot.script`: the collection proxy is the only world-switch owner; confirmed unload → load with generations) or an equivalently verified lifecycle. The level document is **not** sent as a message payload: Lua `msg.post` data is limited to **2048 bytes** in the pinned engine ([`script_msg.cpp:88`](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/script/src/script_msg.cpp#L88), `MAX_MESSAGE_DATA_SIZE`). **Handover contract:** when Play/import is triggered, the loader freezes an **immutable snapshot** of the validated compiled document under a new **snapshot id** + generation. The snapshot id is per load and is **not** the persistent level id: the saved level keeps its identity through ordinary saving and testing, and Play/autosave never create another saved level. The new world loads exactly that snapshot; edits, autosaves or imports during loading create a newer snapshot but never replace the one being loaded. The snapshot id is the reference; the generation rejects stale loads, messages and actions. A snapshot is released only when **no in-flight load still reads it**: after the world reports ready, or, for a superseded load, after that load has actually finished or been confirmed unloaded. Discarding a generation rejects stale results but does not by itself end an in-flight access. Do not simply call the current one-shot terrain builder repeatedly on a live world: old shapes, decorations and pending messages must not survive. Read and validate before replacing the active/saved custom slot. Invalid JSON or a read failure preserves the previous valid level/save. A build failure leaves a safe error state with an explicit retry/import recovery. With no saved custom level, the custom entry point shows Import rather than silently claiming a built-in fallback is the custom course. Use explicit generations/snapshots for async work.
- Determine save organisation before implementing storage. The pinned Defold `sys.save` serializes into a 512 KiB static buffer and heap-allocates larger tables (verified in LE1a, see [Storage](#storage)); do not assume one unbounded table can hold all levels, editor sources and backups. Evaluate a small index plus separate level saves; document actual limits, file sizes and error handling. Catch save errors and retain the last known-good save.
- Verify HTML5 persistence in the pinned engine, including its virtual-filesystem/IndexedDB synchronization. A successful in-memory write is not by itself proof of persistence after reload. Test failure and recovery; UI save status must reflect the completion/error signal actually available.
- Sources: [pinned serializer](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/script/src/script_sys.cpp), [sys API](https://defold.com/ref/sys-lua/), [HTML5 file operations](https://defold.com/manuals/html5/). Runtime verification is still required.

**R15 Edit-mode ownership and input isolation (LE2).** Edit mode is a defined runtime state, not merely a hidden vehicle or zero throttle. Safely suspend/deactivate vehicle gameplay, bounds/crash resets, follow camera and FINISH evaluation while editing; check the chosen mechanism against the pinned engine. This does not pull the complete M4 pause/slow-motion feature into scope. Entering Play builds/restores a canonical attempt through the existing owner/reset path.
- **State ownership:** editor document, Undo history, selection and editor camera live **outside** the proxied world (loader side), so a world reload for Play or a level switch cannot lose them.
- **Loop latency:** LE1b measures custom-level world-switch time **from the Play/import trigger until the vehicle is drive-ready** (not only individual load steps). **LE2 uses the world reload as the baseline.** An in-world rebuild path (second lifecycle, verified teardown per R14) is pursued only if the measured switch time actually disturbs Claudio's build–test loop in his drive test.
- Input gating includes Lua owner, existing GUI messages and HTML/JavaScript listeners (notably the document-level F feedback shortcut), plus browser-fed mobile/tilt commands where applicable. Do not let these bypass Edit mode or a focused field/dialog.
- On mode changes, import dialogs and focus loss, clear held commands, cancel active gestures and cancel/generation-guard pending gameplay actions. Returning focus must not accidentally place an object.

**R16 Two validation layers and stable identity (LE2 onward).** Validate source-document structure separately from gameplay validity: supported versions, finite/bounded input, unique stable object IDs, existing references, legal connection topology, curve/prefab data and explicit document-size/complexity limits. Incomplete authoring states are saveable; malformed structures cannot crash or run unbounded compiler work. The existing station validator remains the authority for compiled station rules. Never silently reduce accuracy or drop geometry to meet a budget.
- Document IDs are independent of Defold object IDs, pointers and physics handles; selection, connections, Undo and future decoration anchors refer to stable document IDs.
- Define the supported v1 terrain domain in LE3, including treatment of self-intersections, reversed segments, loops and one-sided collision orientation. Unsupported forms receive useful errors; arbitrary geometry support is not implied. Logical entry/exit order is separate from engine vertex orientation.

**R17 Undo and selection semantics (LE2–LE5b).** Choose Undo implementation from measured needs; commands are not mandatory. Evaluate bounded source-document snapshots or a hybrid before a complex command framework. Store authoring data, never live physics handles/state or copied textures. One completed action, including connected changes, is one history entry; a new edit after Undo clears the redo branch. View-only navigation is separate from geometry history. Selection is restored/resolved through stable IDs.
- Multi-select drag translates each connected run at most once, even when several selected pieces belong to it.
- Copy/paste allocates new IDs, preserves internal connections, and drops connections to objects outside the copied selection. START/FINISH uniqueness is explicit; ordinary passage duplication must not duplicate singleton markers.
- Prefab preview is a visual/geometry description; it must not require running full gameplay behavior. This boundary is especially important for future dynamic objects.

**R18 Tool scope and usability.** Keep the in-game Defold/Lua/GUI direction and the small HTML file helper. The editor research in #118 is not approval for Qt/Electron, a universal editor, plugins, multiplayer editing or a framework rewrite. Test the actual build → drive → change → Undo → save → reopen workflow with Claudio. Good navigation, readable controls/units, clear selection, cancellable previews and actionable warnings take precedence over a larger asset library. Reusable custom templates later need an explicit independent-copy versus linked-instance policy; no implicit retroactive changes to old courses.

## Screen layout (desktop, Defold GUI)
- **Top bar:** level name · save status · New · Open (my levels / templates) · Export · Import · Undo · Redo · **Play ▶**
- **Left tool palette:** Select (S) · Draw (D) · Curve (C) · Prefab (P) · START · FINISH · Label · Pan
- **Right panel:** properties of the selection (numeric fields: x, y, angle, length, height…), or level properties (name, start speed) when nothing is selected
- **Bottom status:** cursor x/y in metres · active snaps · zoom · warning count (click to list)

## Controls (Edit mode only; game keys keep working in Play)
- **Mouse:** left click selects/places. Left drag moves a selection or handle. Middle drag or Space+left drag pans. The wheel zooms around the cursor.
- **Keys:** E = Play from the editor / back to the editor while driving (R11) · Enter Play · F test start at mouse · S/D/C/P tools · Delete · Ctrl+Z / Ctrl+Y · G grid snap toggle · Shift/Alt/Ctrl as in R6.
- **Esc:** first cancels the current action (drag, polyline), then clears the selection.
- **Text/number input focus:** Defold GUI has no built-in text fields and the project has no text input trigger yet, so name and numeric fields are an **explicit implementation item** (engine behaviour checked against the pinned version). While a field is focused, E, F, Delete, Enter and tool keys act on the field only, never as editor/game actions.
- **All game actions are intercepted centrally while editing** (not a list of individual clashing keys; today the game binds e.g. W/S/A/D, arrows, R, C, F, P, T, H, M, V). Only editor actions are processed in Edit mode; R is disabled. Browser shortcuts (Ctrl+S, Ctrl+W) are not used.

## Editing basics (part of the first usable version)
- **Undo/redo per completed action:** a whole drag is one step; a prefab change including its connected pieces is one step. Undo history survives a test run.
- **Hover highlight:** before clicking it is visible whether an anchor, line, prefab or prefab handle will be picked; overlapping elements can be cycled.
- **Split segment / disconnect / delete point** with a preview of whether deleting a point joins its neighbours.

## Data model
- **Playable export = the existing station JSON** (schema 1, metres) **plus an optional `editor` block** that the game ignores. A **local draft** may have incomplete/invalid or absent compiled station data; its structurally valid editor sources remain recoverable. Draft storage is not advertised as a playable station. Document validation and playable-station validation are separate (R16). The block holds the source objects (polylines, curve anchors with tangents, prefab parameters, connections), settings (grid, sampling tolerances) and versions (R1). The compiled fields are regenerated on Play/Export (R1), so an exported level is directly a valid station file.
- **START / FINISH / checkpoints:** START maps to the existing `spawn` + `start_speed`. FINISH is an optional `finish` object (position + finish line segment + finish direction). **Trigger rule:** FINISH fires when the **chassis centre crosses the finish segment in the finish direction**, detected by a segment test between consecutive physics positions so fast crossings are not missed; "Finish reached" is shown **once per attempt** and re-armed on retry/new test start. Crossing against the direction does nothing. A `checkpoints` list (ordered; position, direction, respawn position) is reserved in the format; v1 writes it empty and the runtime ignores it. Exact field names are fixed in LE2 ([editor shell](#editor-shell-le2)) and validated by `station_data.validate`.
- **Compiler contract:** the compiler writes every field the validator requires: `schema` 1, `units` "metres", a new custom `id` matching `^[a-z][a-z0-9-]*$` (never starting with a built-in station id; e.g. `straight…` would trigger the checker background), `name`, `spawn`, `start_speed`, `run_in`/`run_out` (0 unless set), `bounds` (R13), `chains`, optional `two_sided` (LE3b), `hulls`, `labels`, `finish`, `checkpoints` (empty). No `kind`, `sections` or `markers` in custom levels.
- **No seams in terrain:** a connected run compiles into **one chain** (R4). Hull boxes are only for separate obstacles/platforms.
- **Chain orientation and ghost vertices** are handled by the compiler (solid side below the drawn line, matching the existing stations). Users never see this.
- **Validation** of compiled data for Play/Export reuses the game's own `station_data.validate` (no duplicated station rules); editor structures and references are checked by the separate source-document validator (R16). Station rules today: id and name ≤ 64 bytes each (they travel in every telemetry message, R14 message cap), points ≥ 1 cm apart, ≤ 32 chains, ≤ 2048 points per chain, non-empty terrain, ≤ 64 convex CCW hulls, ≤ 800 render objects (subject to R7), bounds, finite numbers. Bounds are computed automatically with a margin. Drafts may be invalid (R9).

## Storage
- **Locally in the game save** (browser storage on web, app storage later): a list of named levels with last-modified time. Autosave and recovery per R12.
- **Export / Import** a `.json` file (web: download / file picker via the HTML helper). Copy/paste the JSON as text as a fallback. Import opens as a copy (R12).
- **Templates:** all built-in stations are read-only and open as a copy (R2, R3).

### Custom level runtime and save (LE1a)

Implemented in `main/gym/custom.lua` (loader side), `custom.js` (HTML helper), `stations.lua` and `boot.script`. Pinned sources are Defold 1.14.0 `a81dbb0`.

- **Entry and import:** `?station=custom` restores the saved level; with none it shows the Import panel and an error world without a vehicle, never a built-in station. **I** or the **Import level** page button opens the panel: file picker (`.json`) or pasted text. Lua reads it, checks the 256 KiB text cap, decodes, runs `station_data.validate` and rejects a `kind` (station measurement data). An invalid import shows `Import failed: <reason>. The current level and its save are unchanged.` and does not touch the world.
- **Handover (R14):** a valid import is frozen as a loader-owned snapshot (`s<n>`, not the level id) and loaded through the existing `boot.script` unload → load sequence. `configure_station` carries only the snapshot id and generation; the world reads a deep copy. An import during a load is queued and runs after the current load reports ready; snapshots are released once the ready world has read them. Defold 1.14 runs every script and GUI script in one Lua context ([engine.cpp L1409](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/engine/src/engine.cpp#L1409), [L1498](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/engine/src/engine.cpp#L1498)), so the loader module survives world reloads.
- **Build failure:** terrain/decoration creation is guarded; a failure leaves a world without a vehicle, reports `Custom level could not be built`, reopens Import and keeps the previous save. Example: a hull that passes validation but whose vertices Box2D welds (`b2ComputeHull` < 3 points, [shape binding](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/gamesys/src/gamesys/scripts/box2d/v3/script_box2d_shape_v3.cpp#L261)).
- **Placement failure (LE2):** the world reports ready to the loader only after vehicle attach, reset and start succeeded. The start limit is checked again right before placement, and attach/reset/start run guarded: a failure deletes the vehicle objects (only the terrain body remains), reports `the vehicle could not be placed (<reason>)`, reopens Import and keeps the previous save. Spawning the vehicle objects is part of the guarded placement.
- **Save organisation:** two alternating files `sys.get_save_file("rider", "custom-level-a" | "custom-level-b")` (HTML5: `/data/.rider/…`), each `{format=1, seq, text}` with the imported JSON text unchanged. Restore picks the valid slot (format, decode, validation) with the higher `seq`. A save writes the other slot, reads it back and only then counts. An import is saved only after its vehicle is drive-ready (LE2). This slot pair stays the last played or imported level; LE4 adds My levels ([document management](#document-management-le4)).
- **Limits:** import text ≤ 256 KiB, checked before decoding. `sys.save` uses a 512 KiB static buffer and heap-allocates beyond it ([script_sys.cpp L59, L142](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/script/src/script_sys.cpp#L142)); the cap keeps every custom save on the static path. Sample sizes: 0.5–3.7 KiB; a level at the 800-object budget stays far below the cap.
- **Failure handling:** native `sys.save` writes a temp file and renames it; HTML5 truncates the target and unlinks it on a write error ([L262](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/script/src/script_sys.cpp#L262)). The slot pair never overwrites the last good level. A failed save keeps the loaded level and shows `Save failed; the previous saved level is kept (…)`.
- **HTML5 persistence:** `sys.save` only writes the in-memory file system. The pinned dmloader syncs it to IndexedDB asynchronously after every file close and only logs sync errors ([dmloader.js L1342, L1384, L1452](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/com.dynamo.cr/com.dynamo.cr.bob/src/com/dynamo/bob/bundle/resources/web/dmloader.js#L1342)). The sync state is that of the last completed attempt (dmloader resets its failure count on success, and a good sync persists every file written before it). The station line shows `Saving...` until that sync is idle, then `Saved`; a sync error shows `Browser storage sync failed…`, missing IndexedDB `Saved for this session only…`. When the retries are exhausted, dmloader leaves `_syncInProgress` set and never syncs again in that page; the helper wraps `Module._startSyncFS` to record that call and reports it as failed instead of `Saving...` forever. These read and wrap dmloader's internal `Module._sync*` fields, which must be rechecked on an engine update. A file import takes its request number when the file is chosen, so an older, slower read never replaces a newer import. The preview builds share one origin, so the save survives deployments; clearing site data removes it.
- **Input:** the open panel captures game input like the feedback fallback (held commands cleared). Browser keys reach the engine only while the canvas is focused ([library_glfw.js L190](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/external/glfw/js/library_glfw.js#L190)), so typing in the panel never drives. `html5.run` returns the helper's text through `eval` and `lua_pushstring` ([script_html5_js.cpp L91](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/script/src/script_html5_js.cpp#L91)).
- **Evidence:** debug case `le1a` ([gym notes](../../main/gym/README.md#custom-levels)): import A → invalid → B → A with identical shape/sprite/label counts, queued import during a load, retry and bounds reset, real page reloads, an injected Emscripten write error and a build failure. Samples: `main/gym/samples/`.

### Custom level measurement (LE1b)

Report, protocol and phone procedure: [LE1b report](../LE1B_REPORT.md) (debug case `le1b`, generator `tools/gym/levels.cjs`). Desktop results in CI, within the unchanged limits:
- Import → drive-ready takes 55–68 ms (median).
- The longest switch frame reaches 21–26 ms at 612–800 render objects.
- Physics steps stay at the 0.1 ms clock resolution.
- Length up to 99 km costs nothing measurable; Box2D memory grows by about 1 KiB per terrain shape.
- A full level uses 804 of the 1024 sprites (220 left for editor overlays).

Open for later tasks (both handled in LE2, see the decisions below):
- A start 1.5 km or more from the origin fails vehicle placement, and the level is still saved.
- Unbounded text fields versus the 2 KiB `msg.post` cap.

The touch toolbar has its own **Import level** entry ([PR #142](https://github.com/bongohorse/rider/pull/142)). Phone values are NOT RUN until Claudio supplies them. `Level load` in the feedback report shows switch/parse/terrain/decoration times on any device.

#### Decisions after LE1b (Claudio, 2026-10-18)

Each item separates what LE1b **tested**, what is only **assumed**, and what is still **open**. Assumptions are not limits.

1. **Save only a drive-ready level (LE2, before new editor features).**
   - **Rule:** an import or Play result replaces the saved level only after the vehicle is drive-ready. A failure while building or placing the vehicle (including the reset-pose guards) leaves:
     - a safe error state without a half-placed vehicle
     - the previous save unchanged, also across a reload
     - a working re-import
   - **Tested:** after a placement failure LE1b recorded the save status `Saved` for all four failing starts (start-distance series).
   - **Inferred, not tested:** a reload restores the broken level, because LE1a saves when the world reports ready, which is before the vehicle is placed.
   - **Open:** the LE2 tests must show all three outcomes for a real placement failure.
   - **Done in LE2 (`le1a` case):** a real reset-pose failure (both start limits lifted by a debug-only hook) leaves only the terrain body (0 joints), no save status, the Import panel with the reason, the previous level after a reload, and a working re-import.
2. **Provisional start limit: decided |x| ≤ 1 km from the origin; tightened in LE2 to ±500 m in x and y (see below).**
   - **Rule:** applies to START and to temporary test starts (R10), later (proposed) also to checkpoints and other respawn points. It is checked by the source validator **and** in the actual load path before the vehicle is placed, with a clear error message.
   - **Tested:** one start at x = 1000 m was placed; starts at 1.5, 2, 4 and 98.8 km failed `vehicle.lua:68: Noncanonical reset pose`.
   - **Assumed, not proven:** that every allowed start works. ±1 km is a provisional restriction, not a demonstrated safe zone.
   - **Open, LE2 placement tests with the full vehicle (chassis, both wheels, rider; first placement and Retry):**
     - positive and negative positions
     - fractional coordinates
     - different start heights
     - boundary values: exactly ±1000 m, just inside, and just outside (rejected by the validator and by the load-path check)
     - A grid alone does not prove that every position in between works. If any allowed position fails, tighten the limit or choose one of the later options.
   - **Tightened in LE2 to ±500 m in x and y.** The `le1a` placement test found failing allowed starts, so the limit was tightened as this decision requires:
     - A debug sweep runs the full vehicle reset and its pose guards in one world at dense low-discrepancy (fractional) positions, x and y each from its own sequence. Within ±1 km in x and y, 257 of 4000 starts failed (e.g. wheel at y 99969.9922 instead of 99970.0022 units); a first sweep at fixed heights failed from 724 m in x and for every start at a height of 1000 m.
     - Within ±500 m in x and y: 0 of 6000 failed; the largest pose error was 0.0059 units against the 0.01 guard.
     - Cause: below 655.36 m (65536 units) one float32 step is 1/256 unit; above it, 1/128 unit, and the scale conversions then add up to the 0.01 guard. 500 m keeps a margin below that step change.
     - Placement tests with the full vehicle, first placement and Retry: ±500, ±499.99, 123.456, −377.777 (3 m drop), 0.5, heights from −500 to 499.5 m. Just outside (±500.01 in x or y) is rejected by the validator (`Start is limited to 500 m from the origin in x and y`); with only the validator limit lifted, the load path refuses `Start 500.01, 1.70 m is outside the 500 m start limit`.
     - A start that passes the guard is still not a proven safe zone for driving far from the origin (unmeasured).
   - **Not adopted:** a total level extent limit of ±10 km (an estimate). Driving far from the start is unmeasured.
   - **Later options**, only if far test starts or checkpoints are needed:
     - shift coordinates at compile time
     - a guard tolerance that scales with coordinate size. This helps only if the guard alone is the problem; it does not improve physics precision.
3. **Text fields.**
   - **Rule:** a level name of at most 64 characters is a usability rule. The technical limit is the 2048-**byte** `msg.post` payload, which other fields share.
   - **Tested ([PR #140](https://github.com/bongohorse/rider/pull/140)):** the station validator rejects ids and names (and section ids/names) above 64 **bytes**. The `le1a` case loads a 64-byte id with a 64-byte multi-byte name and receives telemetry. A 64-character name with umlauts or emoji can therefore be rejected, because it exceeds 64 bytes.
   - **Open (LE2 tests):** umlauts, emoji and maximum lengths in all text fields at once, checked against the size of the whole message, not only the name.
   - **Done in LE2 (`le1a` case):** a 64-byte id, a name of 16 emoji (64 bytes), 8 labels of 64 bytes (umlauts and emoji) and the URL speed note load and drive. The measurements message was then 1348 of 2048 bytes (`sys.serialize` and `msg.post` share the same table encoder). The current `le1a` result is 1484 bytes, leaving 564 (main run [39263938788](https://github.com/bongohorse/rider/actions/runs/39263938788); the increase came with a later telemetry change, not traced further). A name of 64 emoji (256 bytes) is rejected. The 64-byte limit stays; an ASCII name can use all 64 characters.
4. **World reload stays the Play baseline (R15).**
   - **Tested (desktop CI):** Import → drive-ready median 55–68 ms.
   - **Assumed:** 300 ms as a target for phones. It is a proposed value, not a proven usability limit; Claudio's impression in the drive test counts.
   - **Open:** phone values.
5. **Sprite budget is checked early in LE3,** before the grid and handles are complete.
   - **Tested:** a full level uses 804 of the 1024 sprites.
   - **Assumed until shown otherwise:** hidden sprites still count against the budget.
   - **Done in LE3:** grid, handles and previews are GUI nodes, so they take no sprites; the edit world of the 800-segment sample uses the same 804 sprites as before ([draw tool](#draw-tool-and-connections-le3)).
6. **Touch import entry:** done in [PR #142](https://github.com/bongohorse/rider/pull/142). Covered by touch emulation; phone: NOT RUN.

### Editor shell (LE2)

Implemented in `main/gym/editor_doc.lua` (pure document rules), `editor.lua` (loader-side state), `editor.gui_script` (its own `editor` game object in `boot.collection`), `editor_view.lua` (edit-mode world) and `boot.script`. Debug case `le2` ([gym notes](../../main/gym/README.md#level-editor)).

- **Modes (R11, R15):** E opens the editor on the current level and E/Enter/Play leaves it; both directions reload the world through the existing owner. The edit-mode world has no vehicle, terrain physics, follow camera, bounds/crash resets or FINISH evaluation; it draws the document with release-capable line sprites and labels and follows the editor camera. Play compiles, validates and loads a snapshot like an import; it fails back into the editor with the reason. After a reload, `?station=custom` reopens the editor on the newest draft when no level restores, or when the draft has unplayed changes (draft `revision` ≠ its `compiled_revision`, which a successful Play from START records) and no level was saved after it (saves carry a whole-second `time`; an import made later wins). In a session, E keeps an unplayed document current (also after a test run of it) unless a level was imported after its last change.
- **Input (R15):** Defold stops input propagation only between game objects; components of one object all receive it ([`gameobject.cpp` DispatchInput](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/gameobject/src/gameobject/gameobject.cpp#L3447)). The editor object therefore sits above the loader on the input stack (it re-acquires focus after all inits and on every mode change) and consumes every action in Edit mode. The page shortcuts F (copy report) and I (import) and the page Import button are off while `window.riderEditing` is set; a level import is refused in Edit mode. Focus loss (canvas blur; GLFW releases held keys, [`library_glfw.js` L468](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/external/glfw/js/library_glfw.js#L468)) cancels drags and pans; the first press after it, which brings focus back, is ignored.
- **Controls in LE2:** tools Select [S], START, FINISH, Pan; left click selects/places; dragging START or FINISH is one action; middle drag or Space+drag pans; the wheel zooms around the cursor; Delete/Backspace; Ctrl+Z, Ctrl+Y or Ctrl+Shift+Z; Esc cancels, then clears the selection; F test start on the surface below the cursor, Shift+F drop here; −/+ change the START speed (START selected) or the test start speed (nothing selected) by 0.5 m/s, with Shift by 5 m/s; Template opens a built-in station as a copy. Numeric and name fields are not implemented yet.
- **Document (R1, R16):** `{schema:1, units:"metres", id, name, editor}`. `editor` = `editor_version` 1, `compiler_version` 1, `revision` (one per completed action, monotonic also across Undo), `next_id` (ids `o<n>` are never reused), `objects` (`line` points, `hull` vertices, `label` position/text), `start` {position, speed}, optional `finish` {position, direction ±1}, and `compiled_revision` in compiled levels. The source validator checks versions, finite coordinates (< 100 km), unique ids below `next_id`, ≤ 256 objects, ≤ 2048 points per line, 3–8 hull vertices, ≤ 8192 points in all, 64-byte text. An unknown editor/compiler version is rejected without touching the file.
- **Compiled fields:** the compiler writes every validated station field plus the editor block. `finish` = {`position`, `line` (from 2 m below to 6 m above the flag), `direction` unit vector}; `checkpoints` is an empty list (anything else is rejected); empty lists are written as JSON arrays. Chains run right to left (solid side below). Bounds (R13) = both ends of every terrain and hull edge, labels, the START vehicle box and the FINISH segment plus 10 m (20 m above). START must clear the whole upright vehicle box (x ±0.68 m, y −0.52…+0.68 m) or Play is blocked.
- **FINISH:** fires when the chassis centre crosses the segment (side measured along the segment normal, oriented to the direction) in its direction between two consecutive fixed-update positions; once per attempt, re-armed by Retry; telemetry `finish_count`, `finish_done`, `finish_time`.
- **Test starts (R10):** surface mode places the vehicle 0.9 m above the highest edge below the cursor; drop mode uses the cursor. Both are refused outside the bounds, beyond the start limit or when the vehicle box overlaps geometry. The run uses its own snapshot (spawn and speed replaced) and never replaces the save (status `Test run; the saved level is unchanged`); the draft keeps START. R repeats the test start.
- **Templates (R3):** id `my-<station>`, name `<name> copy`; only chains, hulls, labels and the start are copied, so `kind`, `sections`, `markers`, seam/run-in data and any other field are dropped by construction. The built-in resource is only read.
- **Undo (R17):** bounded snapshots (100) of the authoring document; selection is resolved by id. Replacing the document (template, another level) is one Undo step.
- **Drafts (R9, R12):** `custom-draft-a`/`-b`, same slot-pair format as levels, autosaved 0.4 s after a completed action; status Unsaved / Saving... / Saved / Save failed. A slot with an unsupported version is never overwritten; when it is the newest draft, E refuses only that draft (with a notice) and opens the level or template, saving around it. Play from START saves the compiled level (with editor block) only after the vehicle is drive-ready. The in-memory document or draft is reused only for a level the editor produced; an imported file opens as itself, one Undo step away from the previous document.

### Draw tool and connections (LE3)

Implemented in `main/gym/editor_edit.lua` (pure edit operations), `editor_snap.lua` (R6), `editor_doc.lua` (connections, runs, terrain domain), `editor_overlay.lua` (GUI overlays) and `editor.gui_script`. Debug case `le3` ([gym notes](../../main/gym/README.md#level-editor)).

- **Document version 2 (R1, R4):** `editor_version` and `compiler_version` 2 add `connections`, a list of `{from, to}`: the last point of line `from` is connected to the first point of line `to`. The source validator requires existing lines, each end used at most once, equal end points and no loop. Version 1 documents open upgraded with no connections; their lines compile unchanged. Unknown versions are refused as in LE2.
- **Logical order:** lines are stored left to right where their ends allow it (templates are reversed when opened, Connect reorients a run). "Downstream" therefore means towards the right end of a run. Logical order never decides collision.
- **Runs and compile (R4, D8):** a connected run compiles into one chain with each joint once. Limits: 2048 points per run, 32 chains per level (a two-sided run counts twice).
- **Supported terrain domain (R16; overhangs since LE3b), checked on every compile:**
  - **One-sided runs:** a run that keeps one x direction (vertical steps allowed) compiles as in LE3: one chain written right to left, solid below every non-vertical segment, step walls facing the lower side.
  - **Two-sided runs (decision 2026-10-19):** a run that turns back in x (overhang, curl) or has no x extent (a wall) is two-sided. Box2D chains collide only on the right of each segment ([`manifold.c` L1089ff, Box2D v3.1.0](https://github.com/erincatto/box2d/blob/v3.1.0/src/manifold.c#L1089)), so the station builder adds the same chain reversed at the same place: both sides hold, the inside of a curl and the top of an overhang included. Station JSON field `two_sided`: an optional list of booleans parallel to `chains` (validated by `station_data.validate`). A true entry is drawn once and builds twice, so it counts once towards the 800 render objects but doubles its physics shapes (LE1b measured physics only up to 800 shapes; a level with many two-sided segments is unmeasured). The compiler writes the field only when a run needs it. The self-crossing test walks only the grid cells a segment passes through.
  - Refused with useful errors: points closer than 1 cm, a segment that doubles back onto the previous one (`Line o9 doubles back on itself at (24.00, 7.00) m.`), and a run that crosses or touches itself or closes on itself (`Line o8 crosses itself near (19.00, 5.00) m: a run must not cross or close on itself.`; a grid-bucketed segment test). Connections cannot form loops either: Connect refuses `Connecting these ends would close a loop`. A level without lines or hulls reports `No terrain yet: draw a line [D].`
  - Separate runs may cross; this is not checked.
  - Why two-sided is needed: for a curl ridden from inside, the one-sided rule already holds while the run's right end lies right of its start. The `le3` control course ends left of its start: built one-sided (debug switch), its solid side flips onto the run-up and the vehicle falls through (3 resets). Built two-sided, it drives up the curl past the turn-back point (chassis up to y 4.89 m above the turn at 4.5 m, wheels left of the 15 m wall, no reset).
- **Edit rules (R4, R17):**
  - **Moves:** dragging a line moves its whole connected run. Dragging a point changes only its piece. Dragging a piece's last point, or a joint (which belongs to its upstream piece), moves the whole downstream run by the same displacement. Upstream pieces never move.
  - **Multi-select:** Shift+click adds or removes an object; dragging on empty space selects every object with a point inside the box or an edge crossing it (LE3b). Dragging the selection moves each connected run once.
  - **Points:** a double-click on a selected line inserts a point on the segment (x on the active grid, shape unchanged).
  - **Split [K]** at an inner point makes two connected pieces (no seam).
  - **Disconnect / Connect [J]:** Disconnect orients each remaining run left to right again where it can (LE5a). With a free end selected, Shift+click picks a second free end (orange, with a preview line). Touching ends (within the snap radius, or the picked pair) are joined directly; Connect moves the selected end's run onto the other. Separated ends (LE3b) are bridged by a new two-point piece connected at both ends: neither end moves, and both runs become one run and one chain. Ends of the same run are refused (a loop).
  - **Delete** on an inner point joins its neighbours (orange preview line). On a free end it shortens the line; on a joint it is refused (`disconnect it first`).
  - Every completed action is one Undo step. A refused edit (rule or source validator) changes nothing and shows the reason.
- **Draw [D] (R5):** each click places a snapped point; the readout shows the length and angle of the next segment. A click on the last point, a double-click or Enter finishes the piece; Backspace removes the last point; Esc discards the unfinished piece; Play or E finishes it first. Starting or finishing on a free end shows a connect preview (green ring, readout `connects`); that deliberate placement connects the new piece. The ends are resolved when the piece is finished (a free end exactly at an anchor-snapped first or last point), so Undo/Redo while drawing cannot leave stale connections. Ctrl places without snapping and therefore without connecting. Ctrl+Z while drawing removes the last point. Modifiers and an unfinished piece survive the edit-world reload after a structural edit. Opening another document (template, another level), or Undo/Redo onto another document, discards the unfinished piece and its gesture state (LE3b). Every opened document is a new instance and each Undo entry carries its instance token, so two template copies with the same level id (e.g. `my-straight`) count as different documents.
- **Snapping (R6):**
  - Default: 0.5 m grid plus anchors (line points and hull vertices within 12 px). Alt: 0.1 m grid. Shift: 15° rays with the grid along the ray, from the previous point (draw), the fixed neighbour (point drag) or the grabbed point (move). Ctrl: off. G toggles the grid.
  - Precedence: anchor > angle > grid. The status bar shows the mode and the active snap; the snap point is a diamond (green anchor, blue angle, grey grid, red off).
  - START and FINISH stay unsnapped (START clearance, LE2). A drag starts after 4 px, so a click never moves an off-grid object onto the grid.
  - The page prevents the browser default of Alt while editing. Alt on Windows browsers and Alt+drag on Linux window managers are not verified (CI runs headless Chromium on Linux): drive test.
- **Screen-space behaviour:** pick tolerance 10 px, anchor radius 12 px, handles 9 px, double-click within 0.4 s and 4 px; all independent of zoom. Pixels are those of a 1280 × 720 CSS canvas and scale with the editor GUI, so a HiDPI screen or a larger window keeps them in proportion to the panels.
  - Pick order: line points (every point of a selected line, the ends of every line, a joint once), START, FINISH, labels, then lines and hulls by distance.
  - Hover highlights what a click picks (`point 3 of o4 (1/4, Tab)`); Tab cycles overlapping candidates.
- **Live validation:** a top-bar button shows the error and warning count and opens the list. Errors block Play. Warnings: unconnected ends that touch (a seam the wheels bump on, A18) and START without terrain below.
- **Rendering and budget (R7):**
  - Level geometry stays line sprites and labels. Moves, drags and Undo of moves update sprites in place; adding or removing objects or points reloads the edit world.
  - Grid (≤ 96 lines, ≥ 24 px apart, 1-2-5 steps), handles (≤ 192), previews (≤ 64), the snap marker and the readout are GUI nodes created once: 419 of the editor GUI's 512 `max_nodes`, panels included.
  - Measured at the 800-segment sample (`le3`): the edit world uses 804 sprites (Play's 800 line sprites plus the 4-sprite START box) and 1 label. With its line selected, zoom 0.2 draws 97 handles; at zoom 0.067 the 192-handle pool is full and 51 handles are not drawn. Dropped handles are counted and the status bar asks to zoom in; geometry is never reduced.
  - **Drafts above the budget (LE3b):** the source validator allows up to 8192 points, more than the edit world can draw one sprite per segment. Every line sprite and label is a game object, so two limits apply: `sprite.max_count` 1024 and `collection.max_instances` 1024 (the 4 objects of `world.collection`, START, FINISH and labels count). The budget is checked before building. Above it, each object keeps at least one sprite and the rest are shared out in proportion; a sprite then spans several consecutive points. This affects the display only: geometry, handles, picking and snapping use every point, a warning `Display simplified: … Geometry and handles are exact; Play needs 800 or fewer.` is listed, and Play stays blocked by the station validator. Measured (`le3`): a 1101-point line draws with 1016 sprites, is moved and restores after a reload; 7245 points in 4 lines draw with 1013 sprites.

### Document management (LE4)

Implemented in `main/gym/custom.lua` (My levels storage), `editor.lua` (document instances, keys, clipboard), `editor_doc.lua` (blank level, R1 compatibility), `editor_edit.lua` (copy/paste), `editor.gui_script`, `custom.js` (export download) and `boot.script`. Debug case `le4` ([gym notes](../../main/gym/README.md#level-editor)).

- **My levels (R12):** an index `custom-index-a/-b` plus one slot pair per level `custom-doc-<key>-a/-b`, all in the LE1a slot-pair format (a write replaces the older slot and is read back). The storage key is never reused, so level ids need not be unique and no level is overwritten by another with the same id. The index lists key, id, name and save time; at most 64 levels. An index that exists but cannot be read, or whose newest slot has an unknown format or is invalid (e.g. written by a newer build), is kept unchanged and blocks every My levels write, so no level drops out of the list. A new key is never below a key the page already uses and never one whose level files exist. The index is read once per page: one editor tab at a time.
- **When a level is saved there:** **New** (an empty level, id `my-level-<n>`, START at (0, 1)) and **Import** at once; a template copy or a level opened from a file at its first completed edit (an unedited copy stays out of the list, title `(copy)`); a draft saved before LE4 at its next save. Every autosave (R12, 0.4 s after a completed action) writes the draft (LE2) and the level's My levels copy; the status shows Save failed when either fails. A level that is not fully saved — a failed draft or My levels write, a My levels copy that lags behind its draft (detected on reload, including a missing index entry), or a failed browser-storage sync since the last good one — is saved again before another document becomes current (Open, New, Import, a template, E, or Undo/Redo crossing into another document). If that save fails, or the storage sync has not succeeded again yet (its result arrives asynchronously), the switch is refused (`Not switched: …`); repeating it within 10 s continues anyway, and the unsaved edits then stay only in Undo. When dmloader has exhausted its sync retries the page never syncs again (LE1a), so every switch then needs the repeat.
- **Open:** lists My levels newest first (10 per page; the open level marked) and the built-in templates by name (R2, R3). Opening a level is one Undo step like a template; Undo/Redo between documents keeps each document's storage key, so Undo onto a deleted level saves it again. A My levels entry whose newest slot has an unknown editor version is refused and left unchanged. **Delete** asks once more (`Sure?`) and is not offered for the open level; it removes the index entry, then the files (HTML5 syncs the removal with the next save, [dmloader `FS.close` patch](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/com.dynamo.cr/com.dynamo.cr.bob/src/com/dynamo/bob/bundle/resources/web/dmloader.js#L1383)).
- **Reload:** the draft records its level's key; levels are matched by key, and only levels without one (imported files, saves from before LE4) by id as in LE2. `?station=custom` reopens the unplayed draft as that level (status Saved); a played level records the key it was played from, so E opens that level's latest source rather than an older compiled copy.
- **Name field:** **Rename level** (right panel, nothing selected) starts with the whole name selected: typing replaces it, Backspace clears it, Enter or a click elsewhere confirms (one Undo step), Esc cancels. While it is focused every key types or edits the field only, never an editor or game action. Text comes from the input binding's `text_trigger` (per frame, [`input.cpp` L1008](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/input/src/input.cpp#L1008); HTML5 key presses, [`library_glfw.js` L213](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/external/glfw/js/library_glfw.js#L213)); control characters are dropped and the name keeps the 64-byte limit.
- **Export (R9):** compiles like Play; Play-blocking errors block Export with the first error. The file is the station JSON with its editor block (`compiled_revision` = `revision`), at most 256 KiB, named `<id>.json`, downloaded by the HTML helper, which also shows the text as a copy fallback. A test start is never exported (R10).
- **Import in the editor:** the editor's **Import** opens the LE1a panel (the page shortcut and button stay off while editing). The request carries an editor flag: it is never played or saved as the custom level, also when the editor was left meanwhile (leaving the editor closes its panels). While an Import or Export panel is open the editor takes no input. The file is validated like any import and opens as a new My levels entry, one Undo step away; nothing is played or overwritten. Outside the editor, import works as in LE1a.
- **Round trip:** export → import keeps lines, hulls, labels, START/FINISH, connections, name, id and start speed equal. Only `revision` (monotonic per document) and the storage key change; ids may repeat in My levels.
- **Compatibility (R1):**
  - A supported editor block opens as the source. `compiled_revision` = `revision` claims that the compiled fields belong to this source: a recompile is compared field by field (spawn, start speed, run-in/out, bounds, chains, two-sided list, hull vertices, label position/text, finish position/line/direction; 1 µm tolerance; absent lists count as empty, unknown extra fields are ignored). A difference opens a modal choice naming the first difference (`chains[1][1][2] is 2.000 in the file, 1.500 recompiled`): **Recompile from source** keeps the source; **Keep compiled geometry (as lines)** opens the compiled fields as editable lines (one per chain, no connections), one Undo step back to the source.
  - Stale compiled data (an older or absent `compiled_revision`) is expected after autosaved edits and opens the source without a conflict.
  - An unknown editor or compiler version, or an invalid editor block, is never recompiled: the level's compiled geometry opens as an editable line copy with a notice. The file and the stored data stay unchanged. A draft with an unknown version (no compiled data) is refused as in LE2.
- **Copy/paste (R17):** Ctrl+C copies the selected objects and the connections between them; START and FINISH are singletons and never copied. Ctrl+V pastes at the cursor: the copy's centre moves to the cursor by an offset rounded to the active grid, so on-grid points stay on it. Paste allocates new ids, keeps the internal connections, drops connections to objects outside the copy and selects the pasted objects. The clipboard is authoring data only and survives opening another level. Each paste is one Undo step. Ctrl+D is not used (a browser shortcut). LE4's **Duplicate** (a copy to the right) became **Mirror [<] [>]** in LE5a ([prefabs](#prefabs-le5a)).
- **GUI budget:** the dialogs reuse pooled nodes: 486 of the editor GUI's 512 `max_nodes` (default 512, [`gui_ddf.proto` L278](https://github.com/defold/defold/blob/a81dbb0478e8b73931dc2d671563204f6ac0ef82/engine/gamesys/proto/gamesys/gui_ddf.proto#L278)); LE5a raised it to 640.

### Prefabs (LE5a)

Implemented in `main/gym/editor_prefab.lua` (types, ranges, geometry, handles, mirroring; pure), `editor_doc.lua` (document version 3, runs and chains), `editor_edit.lua` (placement, parameter changes, Mirror), `editor_view.lua` and `editor.gui_script`. Debug case `le5a` ([gym notes](../../main/gym/README.md#level-editor)).

- **Document version 3 (R1, R16):** `editor_version` and `compiler_version` 3 add prefab objects `{id, type: "prefab", kind, at: [x, y], params}`. `at` is the entry (the left end; a Platform's bottom-left corner). The parameters are the source; the geometry is derived and never stored. Version 1 and 2 documents (LE2–LE4) open upgraded to version 3 with the same lines, connections and compiled output, so a version 2 file whose compiled data belongs to its revision opens without an R1 conflict (tested in `le5a`). Builds before LE5a refuse version 3 drafts and levels as unsupported and keep them unchanged ([compatibility](#document-management-le4)). The source validator checks the type, a finite `at`, the parameters (exactly the stored fields, each in range) and that the geometry stays inside the coordinate limit; prefab points count towards the 8192 points and each prefab towards the 256 objects.
- **Types** (metres and degrees; geometry facing right, from the entry):

  | Type | Parameters: range (default) | Geometry | Handles |
  |---|---|---|---|
  | Flat | length 0.5–200 (10) | one segment to (length, 0) | exit: length |
  | Ramp | input angle (default) or height; length (horizontal) 0.5–100 (4); angle −60…60 (15) or height −50…50, at most 60° steep | one segment to (length, rise); the panel shows the other value and the slope length | exit: length and angle (or height) |
  | Step | riser at start (default) or end; height −20…20, at least ±0.05 (0.5); tread 0.5–50 or 0 for a bare riser (4; LE5b) | riser to (0, height), then the tread to (tread, height); riser at the end: the tread first | exit: tread and height |
  | Gap with pit | width 0.5–20 (2), pit depth 0.2–20 (3) | wall down, pit floor across the gap, wall up: (0, −depth), (width, −depth), (width, 0) | exit: width; floor: depth |
  | Kicker + landing | jumps right (default) or left; kicker angle 5–60 (15); lip height 0.1–5 (1); gap 0.5–20 (2); landing flat (default), down or up; landing length 0.5–50 (6); landing angle 1–45 (15, used by down/up) | kicker ramp to the lip at (lip / tan(angle), lip), back wall down to entry level; the open gap; the landing from (kicker length + gap, 0) over its length, flat or sloping down/up by its angle | lip: lip height and kicker angle; gap; landing end: length (and angle) |
  | Platform | width 0.5–50 (6), height 0.2–20 (1) | a hull box with `at` as its bottom-left corner | top-right corner: width and height |

  A Kicker + landing that jumps left is the exact mirror image; its entry is then the far end of its landing.
- **Anchors, ownership and chains (R4, D8):** every terrain prefab is one piece of a run with an entry (first point) and an exit (last point), connected like a line. A composite prefab is one source object: its parts cannot be selected, moved, connected or deleted separately, and its inner points are snap anchors only, never connection ends. A connected run compiles into one chain; only the open gap of a Kicker + landing ends it: the kicker part closes the upstream chain and the landing starts the next. Connecting the composite's entry and exit therefore never adds a collision segment across the gap: in `le5a` no compiled segment spans it, a vehicle dropped above the gap falls out of the level and one dropped on the landing rests on it. The gap has no floor (a pit is the Gap with pit). A Platform is a separate hull obstacle (station `hulls`), never part of a run or a connection. Prefabs always run left to right, so a run with a prefab is never reversed: Connect reverses the other run, or refuses when both contain prefabs.
- **Placement (R5, R6):** **Prefab [P]** lists the six types (keys 1–6 or the list) and previews the shape at the snapped cursor (0.5 m grid, Alt 0.1 m, Ctrl off, anchors). On a free exit the preview continues that run; on a free entry the prefab's exit ends there. Both show the green connect ring, and the click places and connects (deliberate placement); a Platform never connects. A new prefab uses the defaults and is selected.
- **Editing (R4, R17):** the right panel lists a selected prefab's fields. A number field starts with its value selected; while it is focused every key types into it (editor and game keys only type); Enter applies, Esc cancels, a click elsewhere applies it (an invalid value is dropped with the reason). A choice field (ramp input, jump direction, landing type) steps to its next value; switching the ramp input converts the value, so the shape stays (refused with the reason when the converted height would leave its range). Handles (pink) edit the same parameters: lengths snap to the active grid, angles to 1° (Alt 0.1°, Shift 15°), Ctrl turns both off; values stop at their range limits. The exit of every one-part type and of a Kicker + landing that jumps right is its handle (and an end for Connect/Disconnect); a handle on the entry is not offered (edit that value in the panel). Jumping left, the gap handle sits on the kicker's back wall, the side that moves. Dragging the prefab itself or its entry moves its whole connected run. Delete removes the selected prefab (also when one of its ends is selected) with its connections; a prefab has no points to insert, delete or split.
- **Parameter change (R4):** the entry stays fixed, the whole downstream run moves by the displacement of the exit, upstream pieces never move and nothing rotates or deforms. The change with all moved pieces is one Undo step; Undo/Redo restore parameters, geometry and connections exactly. Invalid input (out of range, not a number, a ramp rise steeper than 60°) is refused with the reason, e.g. `Angle must be from -60 to 60 deg (got 75). The previous value is kept.`, and the document stays unchanged. A linear run always keeps its connections; a change that adds a Play-blocking error (e.g. the moved run now overlaps START) is applied and named as a conflict, `Changed, with a conflict: START overlaps flat o3. Undo [Ctrl+Z] restores the previous shape.`; a handle drag shows the same check in its readout before release (Esc cancels the drag).
- **Copy/paste and Mirror (R17):** copy/paste keeps type and parameters, allocates new ids and keeps only internal connections (LE4 rules). **Mirror [<] [>]** in the right panel (replacing Duplicate) places a horizontally mirrored copy left or right of the selection, at least 1 m apart: the mirror axis is rounded to the 0.5 m grid and the offset is a multiple of 0.5 m, so on-grid points stay on the grid. The original and the clipboard stay unchanged. The copy gets new ids and keeps the connections inside the selection, reversed so that it again runs left to right: lines reversed, hulls kept counter-clockwise, labels moved. Prefabs change through their parameters: a ramp's angle or height and a step's height change sign, a Kicker + landing jumps the other way; Flat, Gap and Platform are symmetric. Each Mirror is one Undo step.
- **Persistence:** type, parameters, ids and connections survive autosave and reload, export → import (the file also holds the compiled chains and hulls), copy/paste and Undo/Redo (`le5a`).
- **Budgets (R7, R16), measured in `le5a`:** a prefab is drawn part by part, one line sprite per segment (Flat, Ramp, Step 1; Gap with pit 3; Kicker + landing 3; Platform 4); a parameter change moves sprites in place without a reload. The ten-object course uses 21 sprites. A 255-object draft (95 Gaps with pit and 95 Ramps in one run, 64 Platforms, one 200-point line) draws all 839 sprites without simplification; Play is blocked with `Station render budget exceeds 800 objects` and the document stays unchanged; without the line (636 render objects) it plays with 444 terrain shapes. Prefabs alone cannot exceed 800 render objects without first reaching another limit (64 hulls, 32 chains, or a run that doubles back). The editor GUI has 640 `max_nodes` (raised from 512 for the type list, seven field rows and the Mirror row); 517 are used.

### Curves, Bump/wave and sampling (LE5b)

Implemented in `main/gym/editor_sample.lua` (sampling; pure), `editor_prefab.lua` (Bump/wave, Step), `editor_doc.lua` (document version 4), `editor_edit.lua` (curve edits), `editor_view.lua`, `editor.gui_script` and a read-only debug observer in `controller.script`. Debug case `le5b` ([gym notes](../../main/gym/README.md#level-editor)).

- **Document version 4 (R1, R16):** `editor_version` and `compiler_version` 4 add curve objects `{id, type: "curve", anchors: [{p, in, out, mode}]}` (tangents relative to `p`; mode `free`, `smooth` or `symmetric`; 2–2048 anchors, tangents at most 1000 m), the `wave` prefab and a `sampling` block `{tolerance: 0.005, max_segment: 0.5}` written into every document. Other sampling values belong to a newer compiler: such a document is treated as unsupported (never recompiled; LE4 rules). Versions 1–3 open upgraded with the same lines, connections, prefabs and compiled output; an LE5a Step (a bare riser) becomes a Step with tread 0, the same shape (tested in `le5b` with a version 3 file whose compiled data belongs to its revision: no R1 conflict). Builds before LE5b refuse version 4 documents unchanged.
- **Sampling (R8):** curves and Bump/wave share one sampler with fixed compiler-4 settings: every chord within **5 mm** of the shape and at most **0.5 m** long. The settings follow from LE5a's courses: at 0.5 m a 6 m-radius bend changes direction by about 5° per vertex. Steps:
  - Redundant source points first: consecutive straight Bézier segments on one line in the same direction are merged (their joins are no corners); every other anchor stays a compiled point, so corners are kept.
  - Bézier segments are halved (de Casteljau) until the control points lie within 5 mm of the chord (a rigorous bound: the curve lies in their convex hull) and the chord is at most 0.5 m. A straight piece is cut into equal chords of at most 0.5 m.
  - A Bump/wave interval is halved until width²/8 × the largest |y″| on it is within 5 mm (a rigorous bound on the chord's deviation) and the chord is at most 0.5 m; each wavelength ends exactly at entry level.
  - A piece that would need more than 2048 points is an error (`Bump/wave o5 needs more than 2048 points at 5 mm / 0.5 m sampling: reduce its count or wavelength.`): Play and Export are blocked, the source stays as entered and saveable, and the edit world draws it through its anchors (8 points per wavelength) with the error listed. Nothing is loosened to fit.
  - The compiled points depend only on the source and these settings, never on the zoom: exports at two zoom levels give identical chains (`le5b`). Measured in `le5b`: a 3-anchor curve over 8 m gives 35 points (largest deviation 3.3 mm, longest chord 0.30 m); a Bump/wave 1.5 m × 10 m × 2 gives 65 points (3.6 mm, 0.35 m), both checked against a dense evaluation of the source.
- **Curves (R4–R6):** **Curve [C]** places anchors like Draw places points (snapping as in R6; a click on the last anchor, a double-click or Enter finishes; Backspace removes the last anchor; Esc discards); tangents are set automatically (smooth; a third of the neighbour distance, Catmull-Rom style) and the preview shows the curve. Starting or ending on a free end connects (R5). A selected curve shows its anchors (pink squares) and tangents (lines to pink diamonds; the open ends have none):
  - Dragging an anchor moves it with its tangents (snapped; Shift keeps 15° from the neighbouring anchor). Dragging a tangent changes it (Shift: 15° directions); the partner tangent follows the anchor's mode: smooth keeps both on one line with their own lengths, symmetric mirrors it, free leaves it. **Anchor *i* tangents** in the right panel cycles the mode (free → smooth → symmetric; switching aligns the in tangent).
  - The R4 rule applies: the entry stays fixed, a moved exit anchor moves the whole downstream run by the same displacement, upstream never moves, one Undo step; the first anchor of a connected start belongs to the upstream piece and is not offered (disconnect first). The drag readout shows a new Play-blocking error as a conflict, as for prefabs.
  - A double-click on a selected curve inserts an anchor (de Casteljau split: the shape stays). Delete removes the selected anchor (an end shortens the curve; a connection is refused). Split [K] at an inner anchor makes two connected curves (still one chain).
  - At each joint the neighbour's direction (green) and the curve's (pink) are drawn, and the panel lists the kink angle (`Join to o3: kink 0.0 deg`).
  - Curves can be reversed (Connect reverses a run without prefabs: anchors in reverse order, tangents swapped). Copy/paste keeps anchors, tangents and modes; Mirror reflects the anchors, reverses their order and swaps the tangents with their x negated, so the compiled points are the reflection too.
- **Bump/wave prefab:** height −10…10, at least ±0.05 (default 1; negative heights are dips), wavelength 1–100 (8), count 1–50, whole numbers (1). Shape from the entry: y = height/2 · (1 − cos(2π x / wavelength)) for count wavelengths, so it starts and ends at entry level with a horizontal tangent (smooth joins to flat pieces); its exit is count × wavelength to the right. Handles: the exit (wavelength = length / count, on the grid) and the first crest (height). Mirror keeps it (symmetric). A non-integer count is refused (`Count must be a whole number (got 2.5).`).
- **Step change (Claudio's LE5a drive test, 2026-10-20):** a bare riser looked like a plain line. A Step is now a riser and a tread (default tread 4 m; tread 0 is the old bare riser); **Riser at** start or end; its exit handle sets tread and height; Mirror moves the riser to the other end and changes the height's sign.
- **Edit world:** while a curve or Bump/wave drag changes its sample count, the existing sprites are shared out over the preview's points (spare ones shrink to nothing); the committed change reloads the edit world (the structure signature includes each object's point count).
- **Reference course and protocol (acceptance 1):** Flat 20 m, Bump/wave 0.4 m × 10 m × 2, a curve valley (anchors 40/0, 48/−1.2, 56/0 with horizontal tangents of 8/3 m), Flat 24 m, FINISH at x 74; one connected run (one chain of 131 points). Preset A, START 6 m/s, full throttle (pressed after each start), no brake or lean; Play and two Retries. A debug observer records each completed 1/60 s step with the chassis between x 19 and 57 m. Per run: wheel support losses (A18 support rule), both wheels unloaded, the largest |Δvy| per step and the largest one-step vx drop. Pass: FINISH reached, full throttle on every window step, no support loss, never both wheels unloaded, |Δvy| at most 0.25 m/s per step, and the window crossed in the same number of steps (±1). Result (`le5b`): 0 support losses, 0 airborne steps, |Δvy| at most 0.109 m/s, one-step vx drop at most 0.040 m/s, 336–337 steps. The trial is a defined course under stated conditions, not a universal smoothness guarantee. A first trial with a 0.6 m × 8 m wave (crest radius 5.4 m, nearly 1 g at about 7 m/s) unloaded the rear wheel briefly; that is the hill's curvature, not a seam, so the reference hill was made gentler.
- **Budgets (R7, R16), measured in `le5b`:** the reference course draws 135 sprites in the edit world; with the valley curve selected the editor GUI uses 521 of 640 nodes; the overlay pools (64 lines, 192 handles) hold a selected curve's handles and the drawing preview (at most 56 lines).

### Editable paths: Corner and Smooth points (LE5c)

Requested by Claudio on 2026-10-20 ([#186](https://github.com/bongohorse/rider/issues/186)). Implemented in `editor_sample.lua`, `editor_doc.lua`, `editor_edit.lua` and `editor.gui_script`. Debug case `le5c` ([gym notes](../../main/gym/README.md#level-editor)).

- **Document version 5 (R1, R16):** curve anchors gain the mode `corner` (no tangents; the validator requires both to be zero). A segment between two corner anchors compiles as one straight chord, exactly like a line segment (compiler 5; no 0.5 m chords, no collinear merge across a corner). Version 1–4 documents have no corners and compile unchanged; builds before LE5c refuse version 5 documents unchanged.
- **Corner / Smooth:** **Make smooth** (right panel) works on any point of a selected line or curve that has neighbours on both sides: an inner point or a joint (which belongs to the upstream piece). It never works on an open end.
  - A line becomes a curve with the same id: its connections stay, and every other point becomes a corner, so the untouched segments compile to exactly the same points.
  - The point keeps its position. It gets smooth tangents along the direction from the previous to the next point, each a third of the distance to that neighbour, so the corner is rounded by a curve through the point. Its pink tangent handles shape the rounding; the curve tangent modes (LE5b) apply.
  - **Make corner** removes the tangents: the straight segments come back exactly (tested: the same compiled chain as before smoothing).
  - **At a joint** the upstream piece holds the in tangent and the downstream piece the out tangent; both pieces stay separate objects (and one chain). Dragging either tangent turns the other with it in the same Undo step.
  - Corner/Smooth at a joint with a prefab is refused until that prefab is converted (`Flat o7 is a prefab: convert it to an editable path first to round this joint`).
  - Each switch is one Undo step. A double-click between two corners inserts a corner on the chord.
  - Curved segments use the LE5b sampling (5 mm / 0.5 m) and validation. Measured in `le5c`: a rounded triangle peak gives 39 points, largest deviation 3.5 mm, longest chord 0.49 m.
- **Convert to editable path:** shown for a selected terrain prefab. The first click explains what happens (`Converting removes the Ramp's parameter fields and handles; its shape and connections stay. Click Sure? to convert.`); **Sure? Convert** then replaces the prefab by a line with its current points and the same id, so its connections stay.
  - A Kicker + landing becomes two lines: the landing takes a new id and the downstream connection, and the jump gap stays open (two chains).
  - A Bump/wave becomes a line through its compiled samples (the same shape).
  - A Platform is an obstacle, not a path, and is not converted.
  - Conversion is one Undo step back to the prefab.
- **Persistence:** corner and smooth points and their tangents survive autosave/reload, export → import, copy/paste and Mirror (mirrored anchors keep their modes in reverse order); `le5c`.

## Technical constraints
Single tick owner, once-only unit conversion, Defold-owned bodies/worlds, unchanged reset contract and vehicle tuning, no custom physics or manual stepping. The terrain is rebuilt only through the existing station build path. Editor handles/lines count against the sprite/label limits (1024 each).
